## 1. 한 줄 요약

Twist 프로젝트(NNUE 평가 모델)에서 상태를 신경망 입력으로 바꾸는 encoding을 직접 해 보고 잰 숫자가 몇 개 있습니다. 핵심은 "입력 벡터가 커지면 **어떤 모양으로 저장하고 옮기느냐**가 어디서 encoding하느냐보다 더 큰 문제였다"는 점입니다. 이 자료가 A(Rust가 encoding) / B(Python이 encoding) 중 어느 쪽을 직접 증명하지는 않습니다.

## 3. 이 숫자가 뜻하는 것 (쉬운 설명)

- 체스 판 상태를 신경망에 넣으려면 "칸 x 기물 x 속성"을 긴 숫자 줄로 펼칩니다. 우리 규칙은 카드와 기물 상태가 많아서 이 줄이 1만 5천 칸이 됩니다.
- 그런데 실제 판에서 값이 있는 칸은 약 42개뿐입니다. 나머지 15,000여 칸은 전부 0입니다.
- 15,000칸을 전부 적어서(dense) 옮기는 것은 "책 한 권을 보내면서 99.7%가 빈 페이지"인 셈이고, 값 있는 칸만 적어서(sparse) 옮기면 쪽지 한 장입니다.
- 즉 어디서 만드느냐보다 **몇 개를 어떤 모양으로 옮기느냐**가 메모리와 시간을 좌우했습니다.

## 4. 두 방식 비교 (AlphaZero 방식 사용 기준)

- **A**: Rust 엔진이 encoding해서 Python에 텐서(또는 희소 인덱스)를 준다.
- **B**: Python이 엔진에서 원문(raw) 상태를 받아 직접 encoding한다.

| 관점 | A. Rust가 encoding | B. Python이 encoding |
|---|---|---|
| bridge로 오가는 데이터량 | dense 텐서를 보내면 포지션당 약 61 KB(NNUE 입력 기준). sparse로 보내면 약 0.34 KB. 원문 상태보다 커질 수 있어 형식이 관건입니다. | 원문 상태(보드+카드 슬롯+턴 정보)를 보냅니다. 인코딩된 벡터보다 대체로 작지만, 크기는 아직 측정하지 않았습니다. |
| 입력 설계가 바뀌는 동안의 반복 속도 | 입력 구조를 바꿀 때마다 Rust 수정, 컴파일, PyO3 재빌드, Python 테스트를 거쳐야 합니다. Twist에서도 5,509 -> 15,237로 입력을 한 번 크게 바꿨고 그때마다 학습 가중치를 전부 다시 만들었습니다. | Python(NumPy/PyTorch)에서 바로 고치고 실행할 수 있어 실험이 빠릅니다. |
| 정답지(oracle)와 대조하기 쉬운가 | 규칙 엔진과 encoding이 한 프로세스에 있어 같이 검증할 수 있으나, encoder까지 differential test 대상이 되면 검증 범위가 넓어집니다. | 규칙(엔진)과 encoding이 분리되어, 엔진은 oracle로, encoder는 Python 단위 테스트로 나눠 검증할 수 있습니다. |
| sparse/dense를 어디서 정할지 | Rust가 형식을 정하면 Python 쪽 학습 코드가 그 형식에 묶입니다. | 학습 코드가 필요한 형식(dense 텐서, sparse)으로 바로 만들 수 있습니다. |
| 속도 | encoding이 빠릅니다(Twist에서도 encoding 자체는 병렬로 약 20분/114만 개). MCTS처럼 시뮬레이션마다 encoding하면 차이가 커질 수 있으나 이번 측정에는 없습니다. | Python이 느릴 수 있어 병목이 확인되면 Rust로 옮기는 편이 좋습니다. |

## 5. 권고 (조건부, 결정은 팀이)

아래는 이 자료에서 이끌어낸 제안이며 확정이 아닙니다.

1. **입력 설계가 계속 바뀌는 지금 단계에서는 Python encoding(B)으로 시작**하는 것이 반복 속도 면에서 유리해 보입니다.
2. **bridge 경계를 "원문 상태가 들어가고, 인덱스+값 목록이 나온다"로 잡아** 두면 나중에 encoder를 Rust로 옮겨도 Python 학습 코드는 바뀌지 않습니다. 경계 모양은 유지하고 구현 위치만 옮기는 방식입니다.
3. **전송 형식은 dense 텐서보다 sparse(인덱스+값)를 선호**합니다. Twist에서는 dense가 메모리 한계의 주원인이었기 때문입니다.
4. 입력 구조가 안정되고, **실제 프로파일링에서 encoding이 병목**으로 확인되면 Rust로 옮기는 것을 다시 검토합니다.
5. 반대로 MCTS 시뮬레이션마다 매우 많은 encoding이 필요해 bridge 왕복 자체가 병목이 된다면 A가 유리할 수 있습니다. 이 경우는 이번 자료로는 판단할 수 없습니다.

## 6. 한계와 주의 (솔직하게)

- **NNUE 파이프라인의 숫자입니다.** NNUE는 출력이 값 하나(점수)인 평가 모델입니다. AlphaZero 방식은 정책(policy)과 가치(value)를 함께 내며, **정책 출력 크기가 다르고 아직 정해지지 않았습니다**(행동 공간 설계는 Phase 6). 입력 차원과 희소성(약 42개)은 우리 규칙의 입력 구조에서 나온 값이라 참고가 되지만, 출력 쪽 메모리와 시간은 이 자료에 없습니다.
- ResNet(D-002)처럼 2차원 판 구조를 쓰는 입력은 NNUE의 평평한 특징 목록과 모양이 다를 수 있어, 42개 같은 수치가 그대로 유지된다는 보장이 없습니다.
- 위 표 7번(20k 시험)은 원본 로그를 확인하지 못했고, 8번의 러너 사양(4 vCPU)은 로그에 적혀 있지 않습니다.
- 8, 9번은 GitHub Actions 러너 한 번의 실행 기록이라 다른 환경(로컬, 다른 코어 수)에서는 달라집니다.
- 이 문서는 Rust 또는 Python encoder를 실제로 만들어 비교한 결과가 아닙니다. Python vs Rust 속도 비교 실측은 없습니다.
- 결정은 팀이 합니다. O-001의 상태는 그대로 미결정입니다.
