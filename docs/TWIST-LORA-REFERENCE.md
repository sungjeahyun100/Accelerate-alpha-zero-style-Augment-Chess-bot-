# TWIST-LORA-REFERENCE: Twist의 LoRA 어댑터 구현 (참고 자료)

2026-09-28, 디스코드에서 나온 "토큰 방식으로 가도 저랭크 어댑터는 필요하다"는 논의를 보고, 저희(Twist, `Vamp-pire/Augment-Chess-Engine-Twist`)가 하루 전에 같은 목적(규칙 변경마다 전체 재학습을 피하는 것)으로 만들고 검증까지 끝낸 걸 참고하시라고 남깁니다. **결정이나 제안이 아니라 순수 참고 자료입니다.**

## 배경 (왜 만들었나)
Twist의 NNUE 인코더는 사이트 규칙이 바뀔 때(새 기물/카드 추가, 카드 재조정)마다 입력 차원이 바뀌는데, 지금까지는 차원이 바뀌면 기존 학습을 전부 버리고 처음부터 재학습해야 했습니다. 팀 디스코드에서 나온 문제(대준님: "토큰으로 좌표를 주면 자료구조 확장 없이 기존 모델을 그대로 쓸 수 있다, 저랭크 어댑터만 추가하면 된다")와 같은 동기입니다.

## 설계 요약
- 모델의 입력에 비례해 커지는 두 층(첫 은닉층, 와이드 선형층)을 "옛 입력 칸"과 "새 입력 칸" 두 갈래로 나눕니다.
- **옛 칸**은 이전 학습값으로 초기화하고 동결(고정)합니다. **새 칸**은 0으로 초기화하고 학습만 시킵니다(0 초기화라 학습 시작 시점 출력은 기존 모델과 완전히 동일).
- 기존 카드/기물이 재조정될 때를 위해, 옛 칸 위에 저랭크 보정(B·A, rank 기본 8)을 병렬로 얹습니다. 이것도 0에서 시작합니다.
- 작은 층들(둘째 은닉층 등)은 그냥 통째로 재학습합니다. 크기가 작아 동결할 이유가 없습니다.
- 학습이 끝나면 병합 스크립트가 옛 값+저랭크 보정, 새 칸 학습값을 합쳐서 **평범한 단일 가중치 파일**을 만듭니다. 추론 쪽 코드는 이 병합 결과를 그대로 쓰므로 런타임 변경이 전혀 없습니다.

## 코드 위치 (전부 develop 아님, Twist `master`에 있음)
- `nnue/train.js` — `buildModel()`의 `LORA_BASE`/`LORA_RANK` 분기 (커밋 `09252065`)
- `nnue/merge-lora.js` — 병합 스크립트 (커밋 `ecb7f948`)
- `nnue/train-lora.test.js` — 검증 시험 (커밋 `db8f6fec`)
- `PLAN.md`의 "LoRA 도입" 절 — 설계 설명과 한계 (커밋 `7eb2cfc3`)

## 검증한 수치 (합성 데이터, 실제 학습 아님)
- 학습 0회 시 기존 모델과 예측 차이: 최대 절대 오차 7.4e-7 (사실상 동일)
- 새 입력 칸만 신호가 있는 합성 데이터로 학습 후: 새 칸 가중치는 확실히 움직이고, 옛 칸만 바뀌는 입력의 예측 변화는 평균 0.03 수준([-1,1] 범위 기준)
- 병합 결과를 원래 추론기로 읽은 값과 어댑터 모델 자체의 예측: 최대 절대 오차 1e-6 이내

## 그대로 가져다 쓸 수 없는 이유
- Twist는 JS/TensorFlow.js이고 Accelerate는 Rust/Python/ONNX라서, 코드를 직접 재사용할 수는 없습니다. **설계(옛 것 동결 + 새 것만 학습 + 저랭크 보정 + 학습 후 평범한 파일로 병합)**만 참고하시면 됩니다.
- Twist는 입력 차원이 늘어나는 경우(기물/카드 추가)를 다루고, Accelerate가 논의 중인 건 엔티티 토큰 자체에 좌표를 붙이는 방식이라 적용 지점이 다를 수 있습니다. 다만 "학습 때는 어댑터로 따로, 검증되면 병합"이라는 정책 자체는 동일하게 적용됩니다.

## 확인 안 된 것
- Twist 쪽도 아직 실제 학습(사이트 규칙으로 실제 재학습)은 안 돌려 봤습니다. 합성 데이터 검증만 끝난 상태입니다.
- Accelerate의 엔티티 토큰 구조에 이 저랭크 보정을 그대로 적용할 수 있는지는 검토가 필요합니다(TokEmbedding 테이블에 저랭크를 어디에 걸지는 구조가 달라서 다시 설계해야 할 수 있습니다).
