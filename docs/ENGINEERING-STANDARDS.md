# 개발·검증 기준

이 문서는 신규·변경 코드의 품질 기준이다. 에이전트 진입점은 [AGENTS.md](../AGENTS.md),
기여 절차는 [CONTRIBUTING.md](../CONTRIBUTING.md), 구조 검사의 기계 판정 기준은
[repository-policy.json](../.github/repository-policy.json)이다. 같은 규칙의 복제 문서를
영역마다 만들지 말고 해당 기준을 링크한다.

## 근거와 적용 강도

[JPL Power of Ten 원문](https://spinroot.com/gerard/pdf/P10.pdf)은 C 중심의 안전 중요
코딩 원칙이다. [NASA의 NPR 7150.2D 적용 사례](https://gcn.nasa.gov/docs/contributing/npr7150)는
수용 기준, 변경 추적, 검증 근거를 문서와 PR에 연결하는 방식을 보여 준다.
이 프로젝트는 그 신뢰성 원칙을 조정해 사용하며 NASA 분류·인증·전면 준수를 주장하지 않는다.

규칙 엔진·adapter/FFI·데이터 계약·모델 export는 오류가 후속 계산 전체에 전파되는 경계다.
이 영역에서는 입력 검증, 실패의 명시성, 소유권, 버전, 재현 검사를 엄격히 적용한다.
연구 단계에서는 구조와 파라미터의 실험을 허용하되 결과를 채택·승격한 근거와 구분한다.
기존 JS/C++ 전체를 이번 규약에 맞춰 재작성하지 않는다. 기존 경고와 새 경고를 구분한다.

## Power of Ten 조정표

| 원칙 | 처리 | 프로젝트 기준과 검증 |
|---|---|---|
| 단순 제어 흐름·재귀 금지 | 조정 | 명시적 상태 전이. 탐색 재귀는 깊이·노드·시간 한도로 제한하고 한도 도달을 검사한다. |
| 반복 횟수의 고정 상한 | 조정 | 유한한 입력 순회와 작업/step/시간 제한, 취소 경로. 상한 없는 재시도 금지. |
| 초기화 후 동적 할당 금지 | 조정 | 할당을 허용하되 buffer·batch·캐시 한도와 소유권, 자원 부족 오류를 검사한다. |
| 작은 함수 | 적용·조정 | 하나의 변경 이유와 검토 가능한 인터페이스. 60줄 고정 제한 대신 큰 함수의 책임과 분리 가능성을 검토한다. |
| assertion 밀도 | 조정 | 의미 있는 전후 조건·불변식·경계 오류 검사. 함수당 개수 할당이나 항상 참인 assertion 제외. |
| 최소 변수 범위 | 적용 | 전역 가변 상태 최소화. 게임 상태·RNG·모델·캐시의 소유자와 수명을 명시한다. |
| 입력·반환값 검사 | 적용 | 외부 입력 검증과 오류 전파. 기대할 수 있는 입력 실패에 무조건 unwrap/panic하지 않는다. |
| 전처리기 제한 | 조정 | 표준 매크로·PyO3 derive·필요한 feature/cfg 허용. 지원 조합을 명시하고 복잡한 코드 생성은 피한다. |
| 포인터 제한 | 조정 | raw pointer·unsafe를 작은 FFI 경계에 제한. 안전 근거, 수명·동시성·오류 검사를 둔다. |
| 경고·정적 분석 | 적용·조정 | 변경 영역의 compiler/lint/type 검사. 새 경고는 수정하거나 좁은 범위의 이유를 남긴다. |

규약 예외에는 규칙, 이유, 보완 검사, 재검토 조건을 PR에 남긴다. 정당한 예외 때문에
일상적인 구현 선택을 모두 사용자 승인 대상으로 만들지 않는다.

## 오류·경고와 CI 근거 재사용

개발 도구·검사·CI는 실제 오류 종류, 메시지, 실패 단계와 종료 코드를 보존한다.
실패를 빈 결과·정상 상태·일반적인 안내 문구로 바꾸거나 로그를 숨기지 않는다.
계속 진행할 수 있는 경고도 진단 로그와 보고서에 원인을 남기고, 실행하지 못한 검사와
그 영향을 구분한다. 제품의 사용자 안내를 단순화할 때도 개발 환경의 원래 진단은 유지한다.

서로 의존하지 않는 Rust 검사, 설치 wheel 검사, 동결 JS adapter 검사는 병렬 job으로
실행한다. 같은 목적의 중복 실행은 concurrency로 조율하고, 선행 결과가 필요한 검사만
의존성을 둔다. CI 내부 병렬 worker·메모리 한도와 timeout은 runner 자원에 맞춰 명시한다.

빌드 파일뿐 아니라 성공한 테스트·검증 결과도 재사용할 수 있다. 현재 commit SHA가
달라도 해당 검사에 영향을 주는 소스·공통 계약·fixture·테스트·lockfile·실행 명령과
workflow, OS·runner image·toolchain·환경 조건의 식별자가 같아야 한다. 일부 엔진 파일만
같다는 이유로 전이 의존성이나 검증 입력 변경을 무시하지 않는다. 실행 결과의 근거와
검증 범위를 함께 보존하며, 캐시를 찾았다는 사실만으로 성공을 보고하지 않는다.

현재 [native CI 재사용 도구](../.github/scripts/native-ci-reuse.py)는 stage 0 Git blob과
선택한 runtime·runner 식별자로 `rust`, `native`, `adapter` 범위를 나눠 키를 계산한다.
마지막 필수 검사가 성공하고 근거 보고서를 확인한 뒤에만 success marker를 기록한다.
재사용 시 marker의 동일 입력 식별자와 근거 보고서를 다시 검사하며, 누락·불일치는
정확한 오류로 반환한다. 재사용한 검사의 범위를 현재 실행한 검사와 구분해 보고하고,
adapter의 bounded 검증 결과를 전체 v7 규칙·설치 wheel·프로젝트 완료로 확대하지 않는다.

동결 v7의 실행 식별자는 원문 main·parser SHA, 원문 공개 catalog hash,
[`execution-profile-20260928.json`](../projects/augment-chess/contracts/catalog/execution-profile-20260928.json)의 내용과 실행 profile version,
프로필을 포함한 composite `catalogVersion`을 함께 묶는다. 원문 main/parser가 같아도
startup 초기화 정책이나 manifest가 달라지면 이전 성공을 재사용하지 않는다.
원문 `state.profile.catalogHash`는 원래 공개 hash를 유지하며 composite 식별자로 바꾸지 않는다.
현재 faithful 초기화 프로필은 `accelerate-headless-semantic-v7-faithful-init-v1`이다.
프로필 문서와 검토 요약은 기본 한국어로 작성한다.

CI 키에는 모노레포의 공통 계약, 게임 엔진·게임 계약, native/runtime 및 해당 scope의
Python·oracle·검사·패키징 경로를 전이 의존성으로 포함한다. 실행 manifest는 필수 추적
입력이며 stage에서 빠지면 key 생성에 실패한다. sdist에도 같은 manifest·catalog·crate
manifest가 있어야 하고, 설치 wheel은 소스 배포본의 composite catalog·관측 정책과 일치해야
한다. native 재사용 근거는 Python/OS/runner/toolchain 조건 외에 source ABI 설정,
wheel의 ABI·플랫폼 태그와 실제 설치 바이너리 일치도 보존한다. 현재 ABI는 `abi3-py312`이며,
다른 ABI나 프로필에서 만든 wheel·검증 보고서를 동일 main SHA만으로 승인하지 않는다.
캐시 hit는 보존된 성공 근거의 재사용이고, 이번 실행에서 다시 빌드·검사한 결과와 구별한다.

일회성 workflow는 동일 목표당 하나를 재사용하며 작성자·저장소의 고정 개수 상한은 두지
않는다. 작성자는 목표·담당자·종료 조건을 기록하고 자신의 비활성 임시 workflow와
종료된 실행 기록을 정리한다. 목표당 최근 5개 run, 임시 artifact 14일을 기본으로 하되
열린 PR·연구 자료의 근거나 미해결 실패 기록은 보존한다. 상시 CI·실행 중인 작업·다른
공동작업자의 workflow와 자료를 이 규약을 이유로 정리하지 않는다.

## 에이전트 작업과 검토

1. 변경 상태·기준 커밋·실제 실행 경로를 읽고 관련 계약과 완료 기준을 확인한다.
2. 사용자 요구, 채택된 설계, 제안, 현재 구현, 실행 결과를 구분한다.
3. 담당 영역에서 필요한 변경을 끝까지 수행한다. 미래에 쓸 추상화·복제 구현·빈 디렉터리를
   선제적으로 늘리지 않는다. 기존 영역에 넣을 수 없는 새 책임만 구조 정책에 등록한다.
4. 실패할 수 있는 동작을 중심으로 검사한다. 테스트가 구현의 문장만 재현하지 않게 한다.
5. 별도의 검토 단계에서 실패·취소·자원·동시성·계약·상태 손실을 확인한다.
6. 완료 기준을 실제 결과로 확인하고, 변경 이유·검증 범위·미검증 사항을 보고한다.

불필요한 사용자 확인 없이 승인 범위의 가역적 작업을 진행한다. 중요한 요구의 충돌,
새 비용, 권한을 넘는 외부 변경은 선택과 근거를 구체적으로 설명한다. 다른 작업이나
브랜치의 변경은 보존한다. PR 승인은 기존 팀 리뷰 절차를 따른다.

## 경고와 오류 전달

경고·오류는 경계에서 검사하고 호출자와 개발자가 실제 원인·상태를 알 수 있도록
전달한다. 실패를 빈 결과·기본값·일반 성공 메시지로 바꾸거나 예외·stderr·exit code를
버리지 않는다. 실패한 하위 단계와 이후 복구, 최종 목표의 성공 여부를 각각 기록한다.

### 개발 진단과 제품 메시지

- 개발 CLI·API·테스트·CI에는 실제 경고/오류 유형·코드·메시지, 발생 단계·저장소 상대
  위치, 관련 작업·입력의 식별 정보, 원인 chain과 exit code·signal·상태를 전달한다.
  원인이 확인되지 않았으면 관측 메시지와 미확인 원인을 구분하고 추측을 확정하지 않는다.
  원본에 없는 코드·진단 정보는 없음 또는 미확인으로 표시한다.
- wrapper·FFI·worker·비동기 경계에서 원본 오류의 유형·코드·메시지·원인과 책임 문맥을
  보존한다. 포괄 catch, stderr 폐기, 무조건 성공 exit, `continue-on-error`로 필요한
  실패를 숨기지 않는다. 간단한 최종 요약에서도 정확한 진단이나 접근 가능한 근거를 제공한다.
- 사용자 제품의 화면·공개 응답에는 필요한 상태·안정적인 오류 코드·조치 안내를 제공한다.
  내부 stack·실행 문맥의 상세 진단은 개발 채널에 남겨 개발 환경에서 정확한 오류를
  확인할 수 있게 한다. 제품 메시지를 단순화한다는 이유로 개발 진단도 없애지 않는다.
- 로그·공유 전 비밀·로컬 식별 정보·절대 파일 경로를 제거한다. 오류 코드·수치·원인 의미와
  저장소 상대 위치는 유지하고 정규화·생략을 표시한다. 비밀을 포함한 원문을 먼저 로그에
  저장하지 않는다. 이 기준을 위해 비밀 파일을 읽거나 요약·hash하지 않는다.
- 반복 경고는 같은 유형·메시지·원인 기준으로 묶을 수 있으나 발생 횟수·영향·대표 진단과
  근거를 남긴다. 기존 경고와 새 경고, 미해결 문제와 처리한 문제를 구분한다. 경고를
  해결하지 않고 단순히 log level을 낮추거나 출력에서 없애지 않는다.

### 계속 가능한 경고와 복구

정확성·상태·계약을 유지하는 대체 경로가 있으면 Fail-Operational하게 유효한 작업을
계속할 수 있다. 예를 들어 cache miss·artifact 만료 후 정상 설치·빌드를 수행할 수 있다.
정상적인 cache miss는 실제 상태로 기록하고 존재하지 않는 오류를 만들어 표시하지 않는다.
경고나 실패한 하위 단계의 정확한 메시지, 선택한 복구 경로·이유, 복구의 실제 결과와
남은 영향·미검증 범위를 개발 출력과 최종 요약에 남긴다. 성공한 복구를 원래 경로의
성공으로 바꾸지 않는다.

복구 후 최종 목표와 필수 검사를 충족했다면 최종 성공 상태를 반환할 수 있으며 복구된
경고·오류는 함께 표시한다. 필수 검사 실패·불완전한 출력·손상된 상태·검증되지 않은
계약은 명시적인 실패로 반환한다. 알 수 없는 상태에서 빈 정책·0 점수·무승부·이전 성공을
만들어 계속하지 않는다. retry·자원·시간 예산과 자식 프로세스 소유권을 지키고 OOM 등
실패의 조건·자원 설정을 조용히 바꾸지 않는다.

실제 오류 경로를 변경할 때 전달한 코드·메시지·원인·상태, 안전한 복구와 복구 불가 시
실패를 관련 검사로 확인한다. 원문 전체 snapshot이나 임의의 경고 개수 테스트를 자동
추가하지 않는다. 문서·PR·연구 기록에도 관측한 진단과 실제 복구·미해결 결과를 구분한다.

## 기능 단위 구성과 검사 유지비

SRP는 하나의 기능·변경 이유·소유권에 집중하는 기준이다. 같은 기능의 구현과
관련 보조 코드는 함께 두고, 독립된 책임·재사용·인터페이스 경계가 생기면 분리한다.
작은 함수마다 파일을 만들거나 실험별로 비슷한 구현을 복제하지 않는다. 파일 줄 수나
소스 크기의 합격 기준으로 분할을 강제하지 않는다. 구조 정책의 10 MiB 제한은
무거운 추적 산출물을 막는 기준이며 SRP의 척도가 아니다.

회귀 검사와 fixture는 반복 가능한 중요한 동작을 지킬 때 유지한다. 버그 한 건이나
규약·설계 문구 수정마다 영구 검사를 추가하는 것을 기본 의무로 만들지 않는다.
재발 가능성·영향·기존 검사의 누락과 유지비를 보고 필요한 검사를 선택한다.

- 기존 검사와 fixture를 먼저 활용하고 새 검사는 최소 재현 입력·의미 있는 결과에
  집중한다. 중복 snapshot, 긴 실행 로그, 같은 데이터셋의 버전별 복사본을 쌓지 않는다.
- 신규 fixture는 검증할 계약, 기존 자료로 부족한 이유와 추가 범위를 PR에 설명한다.
  설명을 위해 별도 추적 문서나 전용 관리 도구를 만들지는 않는다.
- 일회성 조사 입력·출력·진단 로그는 `%APPDATA%\Accelerate\reports`에 둔다.
  이후 지속 검증이 필요해진 최소 재현 자료만 소스 fixture로 채택한다.
  협업자가 재사용할 설정·결과·한계는 아래 연구 영수증 기준으로 별도 선별한다.
- 구조 검사·CI와 여러 기물·카드 계약을 검증하는 공통 비교 자료는 실제 사용 가치를
  기준으로 유지한다. 파일 개수·테스트 개수의 고정 할당량을 두거나 기존 유효한
  검사를 일괄 제거하지 않는다. 관련 코드를 바꿀 때 중복·폐기된 검사도 함께 검토한다.

## 공유 연구 영수증

연구 영수증은 협업자가 재사용할 목적·재현 방법·관측 결과·해석·한계를 선별한
Markdown 문서다. 조사, 규칙 비교, 성능 실험과 실패 분석에 사용하며 성공·실패·
중단·결론 불충분을 보존할 수 있다. 단순 Git 작업과 반복 확인마다 문서를 만들지
않는다. 원시 실행 영수증·로그는 외부 생성물 루트에 유지하고 공유 요약을 별도로 만든다.
공유용 정규화 때문에 원본 기록이나 그 hash를 바꾸지 않는다.

### 디렉터리와 이름

- 선별한 공유 초안과 채택 문서는 `docs/research/`에 평면 구조로 둔다.
  [범용 템플릿](research/TEMPLATE.md)을 복사해 작성하고 개인별·실행별 폴더를 만들지 않는다.
- 파일명은 `YYYY-MM-DD--topic--github-login.md`다. 날짜는 최초 작성일의 UTC 날짜,
  주제는 소문자 영문·숫자·하이픈, 작성자는 확인한 공개 GitHub 로그인명을 소문자로 쓴다.
  같은 이름의 별개 기록은 확장자 앞에 `--02`, `--03` 순으로 붙인다.
- GitHub API·인증 계정 정보 또는 작성자가 명시한 공개 GitHub 프로필로 작성자를 확인한다.
  OS 계정명·홈 경로·Git 표시 이름이나 이메일에서 추정하지 않는다. 미확인 초안은
  공유 전 작성자를 확인한다. 공동 작성자는 본문에 추가하고 기존 파일명은 유지한다.
- 같은 연구 질문의 반복 실행은 기존 영수증의 결과 표에 묶는다. 새 연구 질문은 별도
  기록으로 만든다. 정정 시 변경 이유·기존 결론의 영향과 후속 기록을 연결한다.
- 작은 선별 Markdown은 기존 `docs` 책임 영역에서 관리한다. 원시 로그·반복 snapshot·
  모델·데이터셋·바이너리는 넣지 않는다. 큰 표나 생성물을 허용하려고 광범위 구조 정책
  예외를 추가하지 않으며 기존 10 MiB 제한도 그대로 적용한다.

### 재현과 공유 경계

본문에는 작성 시점·GitHub 작성자·관련 PR/이슈, 저장소와 기준 commit SHA, 목적·
성공 기준·비교 대상, 재현 명령·입력·seed·버전, 환경·자원 한도, 핵심 결과와 한계를
남긴다. 미커밋 변경이 있으면 영향 파일을 저장소 상대 경로로 기록하고 해당 결과를
clean commit의 결과로 표시하지 않는다. 정확한 재현에 필요하면 검사한 diff나 입력의
hash와 접근 가능한 근거를 연결하며 큰 원본을 문서에 복사하지 않는다.

로컬 검사, CI 요청, 관측한 CI 성공과 모델 성능 검증을 각각 구분한다. 실행하지 않은
것은 **미실행**, 측정하지 않은 값은 **미측정**, 적용되지 않는 것은 **해당 없음과 이유**로
표시한다. 관측 사실과 추론을 분리하고 표본·반복 수를 남긴다. 실패·중단 결과를 성공이나
실제 무승부로 바꾸지 않는다. 공유하지 않는 원시 자료가 있어도 핵심 결과와 한계를
이해할 수 있게 작성한다.

공유 본문, 명령, 오류 메시지와 발췌에는 절대 파일 경로, 로컬 계정명·실명·호스트명,
개인 이메일·장치 식별자와 비밀 값이 없어야 한다. Windows·Unix·WSL 경로에도 같은
조건을 적용한다. 저장소 상대 경로 또는 `${ARTIFACT_ROOT}` 기준 상대 경로를 쓰며,
이 기호는 생성물 루트의 문서용 표기다. 실행할 때 환경에 맞게 지정하되 확장된 로컬
값은 공유하지 않는다. 공개 GitHub 식별자와 저장소·PR·CI 링크는 사용할 수 있다.

외부 산출물은 논리 루트 기준 상대 위치나 인증 정보 없는 공유 참조와 필요한 hash로
연결한다. 임시 서명·인증이 포함된 다운로드 URL은 쓰지 않는다. 접근 제한·만료가
재현에 영향을 주면 한계에 기록한다. 명령·발췌를 정규화해도 옵션·seed·수치·오류 의미는
보존하고, 생략·정규화가 해석에 영향을 주면 밝힌다. 이 점검을 위해 비밀 파일을
읽거나 그 내용을 요약·hash·보관하지 않는다.

### 채택과 보존

에이전트는 내용·민감정보·재현성을 점검한 공유 초안을 PR에 포함한다. 별도 사전 사람
승인 절차를 추가하지 않으며 기존 PR 리뷰와 병합으로 공동 연구 자료에 채택한다.
연구 자료 채택은 CI 성공, 전체 구현 완료, 배포 승인과 모델 승격을 의미하지 않는다.
실행 근거의 종류와 실제 관측 범위를 별도로 유지한다.

채택 문서는 캐시나 기간 기준으로 자동 삭제하지 않는다. 폐기된 결론은 후속 기록에
연결해 표시하고, 중복 자료의 통합·제거는 일반 PR 리뷰로 처리한다. 기존 일회성 로그를
일괄 이관하거나 일시적인 원시 자료마다 Git 문서를 만들지 않는다.

이 경계는 Clearra의 [관리 정책](https://github.com/daejunnom/Clearra/blob/f97dd20839daf3a42e3a32483c990cc91a44d927/docs/management-policy.md)과
[에이전트 규약](https://github.com/daejunnom/Clearra/blob/f97dd20839daf3a42e3a32483c990cc91a44d927/AGENTS.md)의
로컬 실행 기록과 선별한 연구 요약을 구분하는 원칙을 참고했다. Accelerate의 기존
생성물·WSL 실행 기준을 따르며 Clearra의 실행 관리자나 영수증 schema를 도입하지 않는다.

## 일회성 CI 개수와 정리

일회성 CI는 특정 조사·실험을 위해 만들고 목표 달성 또는 중단 시 제거할 임시 workflow다.
수동 `workflow_dispatch`를 제공한다는 이유만으로 지속 사용하는 학습·자가대국·비교
workflow를 일회성으로 분류하지 않는다. 저장소의 상시 CI와 필수 병합 검사는 유지한다.

### 파일과 실행의 한도

- 기존 workflow의 입력과 관련 검사를 먼저 재사용한다. 새 임시 파일은
  `.github/workflows/oneoff--topic--github-login.yml`에 둔다. 주제·확인한 GitHub 작성자
  표기는 연구 영수증과 같으며 반복 실행마다 이름·파일·브랜치를 늘리지 않는다.
- 같은 목표당 임시 workflow 1개를 공동작업자·checkout·브랜치·에이전트 전체에서
  재사용한다. 작성자·저장소 전체의 고정 개수 상한은 두지 않는다. 여러 브랜치에 있는
  같은 파일의 수정본은 한 workflow로 보며, 같은 목표를 다른 이름·작성자로 복제하지 않는다.
- 생성 전 관련 PR과 Actions 목록에서 같은 목표의 파일, 소유자·공동작업자와 실행
  상태를 확인한다. 공동 workflow는 확인한 공개 GitHub 책임 작성자 1명과 공동작업자를
  기록하고 종료·정리 책임을 명확히 한다. 소유권 이전은 관련 PR에 합의와 이유를 남기며
  같은 목적의 파일을 새 작성자 이름으로 복제하지 않는다.
- 조사·후속 작업이 남았거나 정리가 끝나지 않은 임시 파일은 계속 추적한다. disable한
  파일도 정리 완료로 표시하지 않는다. 고정 파일 수 상한이 없어도 실행 비용·runner·
  worker·GPU 사용은 기존 자원 기준과 공동 작업 조율을 따른다. 다른 사람의 작업을
  정리해 자리를 만들지 않고 소유·상태가 불명확하면 보존하고 설명한다.
- PR에 목표·책임 작성자·공동작업자·파일 경로·시작 시점·완료 또는 중단 조건, 실행 횟수·시간·
  worker·메모리·artifact 예산과 취소·정리 방법을 남긴다. 전용 추적 저장소나 큰 로그를
  추가하지 않는다. 임시 CI를 필수 병합 검사나 영구 schedule로 등록하지 않는다.
- 같은 목표의 run은 동시에 1개만 실행한다. 재실행 전 queued·pending·in-progress
  상태를 확인하고 기존 실행이 끝나기 전에 중복 dispatch하지 않는다. 자기 작업과
  합의한 공동 workflow의 재생성 가능한 작업에 concurrency를 적용하며 다른 목표의
  run과 취소 그룹을 공유하지 않는다. 공동 작업의 취소 조건도 관련 PR에 기록한다.
  변경 없는 실패를 무한 재실행하지 않고 미리 정한 횟수·자원 예산 안에서 종료한다.

기존 임시 workflow는 다음 관련 작업에서 목적·소유·종료 조건을 확인해 이 기준을
적용한다. 이름만 보고 파일이나 원격 실행 기록을 일괄 변경·삭제하지 않는다.

### 완료 후 정리와 관측 근거

목표 완료 또는 중단 후 소유자는 해당 workflow의 실행·대기 작업과 다른 PR의 사용이
없음을 확인한다. 필요한 경우 자기 임시 workflow를 disable해 새 실행을 막고 PR에서
파일을 제거한다. 다른 에이전트의 실행을 임의로 취소하거나 상시 CI를 비활성화하지 않는다.
계속 유지할 필요가 생기면 일반 PR 리뷰로 상시 책임·검증·자원 예산을 정하며 임시 분류로
한도를 우회하지 않는다.

workflow 파일, 실행 기록, 로그·artifact는 서로 다른 정리 대상이다. 파일 제거만으로
run·artifact 정리가 완료되었다고 보고하지 않는다. 종료된 자기 임시 run만 정확한
repository·workflow·run ID와 상태·참조를 확인해 정리한다. 실행 중·대기 중인 작업,
열린 PR의 필수 확인 근거, 미해결 실패, 모델·배포·릴리스 근거와 공동 연구 자료가
의존하는 원본은 개수나 기간만으로 삭제하지 않는다. 유지 예외의 이유와 재검토 조건을
관련 PR 또는 연구 기록에 남긴다.

일반 종료 run은 목표당 종료 시점이 최근인 5개를 남기고 이전 반복·중복 기록을 정리한다.
이 개수는 서로 다른 run ID로 세며 re-run attempt를 별도 run으로 세지 않는다. 성공·
실패 여부로 보존 순서를 바꾸지 않는다. 위 보존 예외는 별도로 유지하고 이유·참조·
재검토 조건을 남긴다. 실행 중인 작업을 개수 제한에 맞추려고 취소하지 않는다.

새 임시 artifact의 기본 보존 기간은 `retention-days: 14`다. 저장소가 허용하는 한도
안에서 설정하고 실제 만료 조건을 기록한다. 모델·데이터·연구·배포 근거로 보존할
산출물은 만료 전에 기존 외부 생성물 영역으로 보존하고 필요한 hash·접근 참조를 남긴다.
이 설정은 업로드 artifact의 보존 기간이며 run·로그 전체의 기간 설정이 아니다.
로그·run의 실제 보존은 저장소 설정과 명시적인 정리 결과를 따로 확인한다. 이번 문서
변경으로 저장소 전체 retention 설정이나 기존 상시 CI의 기간을 변경하지 않는다.

삭제·만료 전 기준 SHA·run ID/attempt·관측 상태·핵심 결과·한계와 필요한 산출물의
hash·접근 가능한 위치를 PR이나 연구 영수증에 선별해 남긴다. 보존할 큰 산출물은 기존
외부 생성물 영역에 둔다. 링크만 남겨 유일한 근거가 사라지지 않도록 하고, 삭제·만료로
접근할 수 없어진 근거와 그로 인한 재현 한계를 기록한다. 실패 기록을 삭제해 성공으로
보이게 만들지 않는다. 실제 삭제·보존 결과와 예외를 최종 보고에 적는다.

이 기준은 에이전트의 생성·실행·정리 규약이다. 현재 메타데이터 구조 검사가 원격
workflow 개수나 run 참조·보존 기간을 자동 통제한다고 주장하지 않는다. 문서 채택을
기존 workflow나 저장소 Actions 설정의 일괄 변경으로 취급하지 않는다.
[workflow 비활성화](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows),
[동시 실행 제어](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency),
[artifact 보존](https://docs.github.com/actions/configuring-and-managing-workflows/persisting-workflow-data-using-artifacts),
[실행 기록 삭제](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/delete-a-workflow-run)의
실제 동작은 GitHub 공식 문서를 따른다.

## CI 병렬화와 결과 재사용

이 기준은 상시 CI와 일회성 CI 모두에 적용한다. 독립 검사는 가용 GitHub Actions
runner를 활용해 병렬화하고, 같은 호환 빌드를 반복하는 비용은 artifact·cache 재사용으로
줄인다. 성공한 테스트·검증 결과도 영향 입력이 같으면 재사용한다. 자원 사용과 검증
의미를 함께 유지하며 문서 채택을 실제 속도 개선으로 보고하지 않는다.

### 입력의 동일성과 영향 범위

재사용 단위는 빌드 대상 또는 개별 테스트·검증 묶음이다. SHA가 달라도 주요 엔진,
빌드·테스트 파일과 결과에 영향을 주는 입력이 같으면 재사용할 수 있다. 문서·PR 설명
등 해당 검사와 무관한 변경 때문에 모든 빌드·검사를 반복하지 않는다. 검사별 실제
의존 입력 집합과 content fingerprint를 정하고, 변경 파일과 입력을 그 집합에 대조한다.

입력에는 관련 엔진·라이브러리, 빌드 script·manifest·도구 버전·옵션, 테스트·검증 코드,
fixture·생성기·oracle·bridge 계약·모델·데이터·seed와 관련 환경을 포함한다. 현재
workflow의 조건·matrix·실행 명령이나 입력 범위가 바뀌면 해당 결과의 재사용 조건도
다시 확인한다. 파일명·engine 디렉터리만 같은 것으로 판단하지 않고 간접 의존 입력도
포함한다. 반대로 관련 없는 문서, 커밋 메시지·작성 시각은 입력 집합에 넣지 않는다.

OS image·toolchain·의존성은 이름표만 비교하지 않고 결과에 영향을 주는 실제 버전을
확인한다. 재사용 근거에는 원본 SHA·생산 run ID/attempt·검사 범위·성공 상태·입력
fingerprint와 현재 대상 SHA·동일성 확인을 남긴다. 영향을 받는 검사만 재실행하고,
입력 집합이 불완전하거나 출처·환경·결과를 확인할 수 없으면 해당 단위를 정상 실행한다.
현재 Git index·변경 문서, 시각에 따라 달라지는 외부 서비스·사이트·보안 정보처럼
변경된 대상이나 새로운 관측을 요구하는 검사는 그 새 입력에 대해 확인한다.

### 병렬 작업과 자원 예산

- 독립적인 정적 검사·규칙 비교·OS 검증은 별도 job 또는 matrix로 실행한다. 산출물이나
  완료 상태를 실제로 요구하는 작업에만 `needs`를 둔다. 한 run 안의 step을 직렬로
  나열하거나 서로 다른 목표를 한 취소 그룹에 묶어 불필요하게 병목을 만들지 않는다.
- 일회성 CI의 목표당 동시 run 1개는 중복 dispatch 방지 규칙이다. 그 run의 독립 job·
  matrix·shard는 병렬로 실행할 수 있다. 병렬 job 수는 가용 runner와 자원 예산으로 정한다.
- job별 CPU·메모리·GPU·worker·스레드·timeout과 병렬 job 수를 함께 계산한다.
  동일 runner의 worker·스레드 과다 생성이나 여러 job의 공유 GPU·외부 자원 경합을
  피한다. 가용 runner·계정 동시 실행 한도와 작업 예산을 활용하며, `max-parallel`은
  실제 자원·비용·공동 작업 제약에 근거해 정하고 이유를 PR에 남긴다. 실제 제약이
  없으면 GitHub가 허용하는 독립 job 병렬화를 활용한다.
- shard는 입력·seed 범위를 결정적으로 나눈다. 집계에서 중복·누락·실패·중단·취소를
  확인하고 유효한 표본만 분모에 넣는다. 실패·취소 shard를 성공이나 실제 무승부로 채우지 않는다.
- 여러 OS·shard의 결과를 모두 수집해야 하는 비교는 `fail-fast: false`를 사용한다.
  계속 실행할 가치가 없는 비싼 후속 작업은 선행 실패 시 중단한다. 선택한 실패 처리와
  취소된 검사의 미검증 범위를 기록하며 `continue-on-error`로 필수 실패를 성공 처리하지 않는다.
- matrix job의 출력은 OS·대상·profile·shard별 경로와 artifact 이름으로 분리한다.
  여러 job이 같은 산출물을 덮어쓰거나 하나의 cache에 경합해 쓰지 않도록 한다.

### 빌드 산출물과 cache의 경계

| 재사용 대상 | 용도 | 확인과 복구 |
|---|---|---|
| 빌드 artifact | 후속 job·검사에 동일 빌드 전달 | 생산 출처·입력·환경·파일 digest 확인, 유실·불일치 시 재빌드 또는 명시적 실패 |
| 성공한 테스트·검증 근거 | 영향 입력이 같은 검사 결과 재사용 | 실제 완료·성공·검사 범위와 fingerprint 확인, 입력 변경·근거 유실 시 해당 검사 재실행 |
| 의존성 cache | 다운로드·설치 가속 | 도구·의존성 fingerprint와 신뢰 경계 확인, miss 시 정상 설치 |
| 컴파일 중간 cache | 호환 환경의 증분 빌드 가속 | OS·target·toolchain·옵션·입력 무효화 확인, build 도구의 재검사·재빌드 수행 |

호환되는 빌드는 producer job에서 한 번 수행하고 `needs`와 artifact 전달로 후속
테스트에 제공한다. OS·아키텍처·target·toolchain·ABI·profile·feature·빌드 옵션,
소스·의존성·생성 입력의 fingerprint가 다른 빌드는 분리한다. 플랫폼 독립 자료를
공유할 때에도 형식·버전 호환성을 확인한다. 필요한 입력이 누락된 넓은 cache key나
파일명만으로 완성된 바이너리의 호환성을 판단하지 않는다.

공유 빌드에는 생산 repository·workflow·run ID/attempt·기준 SHA, 위 환경·입력
fingerprint와 파일 digest를 남긴다. 소비자는 검사할 SHA와 생산 출처·실제 파일을
확인한다. 다른 SHA 사이에서 재사용하려면 결과에 영향을 주는 모든 입력이 동일하다는
근거가 필요하다. 확인할 수 없으면 해당 대상에서 다시 빌드한다. 이전 workflow run의
artifact도 이름이 같다는 이유만으로 최신·정상 결과로 취급하지 않는다.

digest나 출처·호환성이 불일치하면 재사용을 중단하고 재빌드 또는 명시적 실패로
처리한다. digest가 일치해도 생산자의 신뢰와 입력 일치를 별도로 확인한다. artifact
도구의 경고만으로 검증 완료를 주장하지 않는다. 재사용한 빌드와 현재 실행한 테스트를
구분한다. cache hit만으로 성공한 검사 근거가 있다고 판단하지 않는다. 이전 성공 결과의
영향 입력과 검사 범위가 같으면 아래 기준으로 재사용하고, 변경된 검사는 재실행한다.

cache key에는 용도·OS·아키텍처·도구 버전과 관련 의존성·입력 fingerprint를 반영한다.
중간 cache의 부분 일치는 build 도구가 입력을 다시 검사하는 가속 용도로만 사용한다.
cache miss·만료 시 정상 설치·빌드 경로가 동작해야 한다. 임의의 다른 OS 바이너리나
출처가 불명확한 이전 결과로 대체하지 않는다. 비밀·credential·보존할 모델·데이터·
보고서는 cache에 넣지 않고 신뢰하지 않는 PR이 쓴 cache·artifact를 더 높은 권한의
빌드·배포 경로에서 검증 없이 실행하지 않는다.

파일·manifest·공유 명령에는 저장소 상대 경로 또는 논리 생성물 경로와 공개 GitHub
출처를 사용한다. 절대 로컬 경로·계정명·호스트명·비밀을 공유하지 않는다. 생성물 루트와
OS별 캐시 분리는 기존 기준을 따르고 cache의 용도·크기·보존·무효화 방법을 기록한다.
artifact는 해당 workflow의 보존 기준을 따르며 일회성 자료는 기본 14일이다.
연구·모델·배포 근거의 별도 보존 조건은 기간·개수 정리보다 우선한다.

### 성공한 테스트·검증 결과

필요한 검사가 실제 완료·성공했고 영향 입력·옵션·환경·검사 범위가 동일한 결과를
재사용한다. 근거가 되는 job·matrix·shard와 유효한 표본·검사 수를 확인한다. 실패·
중단·취소·미실행 결과나 `continue-on-error`로 가려진 실패를 성공 근거로 쓰지 않는다.
다른 독립 job의 실패를 이유로 실제 성공한 검사까지 무조건 재실행하지는 않되, 필요한
선행 입력의 성공·무결성과 이번에 필요한 전체 검사 범위를 확인한다.

현재 SHA에서도 재사용 조건을 확인하고 job summary·결과에 원본 SHA·run 참조·
fingerprint·검사 범위와 재사용 여부를 남긴다. GitHub 필수 check가 있다면 현재 대상
SHA의 확인 job이 재사용 근거를 검증해 상태를 내도록 한다. 이전 SHA의 성공을 새
SHA에서 직접 실행한 검사로 표시하지 않고 재사용 확인의 성공으로 구분한다.
근거가 만료·삭제되었거나 검사 범위·입력 동일성을 확인할 수 없으면 해당 검사를 실행한다.

빌드·검사 결과의 재사용은 모델 승격·배포·릴리스 승인과 별개다. 독립 재실행이나 현재
대상에서의 관측이 완료 조건이면 그 검사를 수행한다. 일회성 run 최근 5개·artifact
14일 정리에도 필요한 재사용 근거의 별도 보존 조건을 적용하고, 모든 일반 실행마다
연구 영수증이나 영구 fixture를 추가하지 않는다.

### 변경 후 확인

CI를 실제 변경할 때 관련 병렬 job·shard 집계와 빌드 artifact 소비, 성공 검사 근거의
재사용, 영향 입력 변경 시 재실행과 cache miss·만료·불일치의 정상 실행·실패 경로를
확인한다. 정상 cache 경로만 통과한 결과를 clean build 검증으로 표시하지 않는다.
일회성 시험 자료를 영구 fixture로 자동 추가하지 않고 기존 관련 검사와 제한된 실행을
활용한다. job 수·대기·빌드·검사 시간, 재사용 여부와
실제 실행·재사용·미검증 범위를 남기며 성능 개선은 관측한 비교 결과로 보고한다.

job 의존·matrix·실패 처리는 [GitHub workflow 문법](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax),
산출물 전달·digest·보존은 [artifact 문서](https://docs.github.com/en/actions/tutorials/store-and-share-data),
cache 접근·복원은 [cache 기준](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)을 참고한다.

## 경계별 완료 기준

원격 반영이 승인된 작업의 커밋·공유 기본값은 일반 PR 1~3개 논리 커밋, 짧은 작업의
최종 1회 push다. 1시간 초과 작업은 검증된 중간 단계를 공유하고 장기 작업은
60~90분마다 완료 단위가 있는지 확인한다. 시간이나 개수를 맞춘 미완성 커밋은 금지한다.
구체적인 협업 절차는 [CONTRIBUTING](../CONTRIBUTING.md#커밋-크기와-원격-공유-빈도)을 따른다.

| 변경 | 필요한 근거 |
|---|---|
| 저장소 규약·문서 | 문서 간 책임·구현 상태의 일치, 링크, 구조 검사와 그 오류 경로 |
| 규칙 엔진 | 실제 실행 경로의 legal/apply/result, 거절 상태 보존, 턴·종료·RNG, 비교 fixture |
| PyO3 바인딩 | 직접 호출과 JSON의 논리 동등성, 소유권·수명·오류·취소, 필요시 GIL 해제 후 안전성 |
| encoder·데이터 | 충분한 상태/관측 보존, action과 정책 정렬, dtype/shape, 규칙·카탈로그 버전 |
| 모델·ONNX | policy/value 수치 비교, 유한값·mask·batch, FiLM 조건 입력, export 메타데이터 |
| LoRA 병합 | 원본 보존, 호환성·고정 조건 확인, 병합 전후 수치와 성능의 별도 비교 |
| 모델 승격 | 정확성 검사에 더해 독립 seed·색 교환 대전과 정해진 통계 기준 |

일부 signature 일치나 JS 자신과의 회귀를 전체 상태·사이트·Rust 동등성의 증명으로
보고하지 않는다. 실행하지 않은 Rust/Python/ONNX 검사는 미실행으로 기록한다.
학습을 중단한 대국을 실제 무승부·패배 결과처럼 저장하지 않는다. 같은 편 추가 행동이
있으면 MCTS value 부호는 실제 행동자가 바뀔 때 전환한다.

모델 승격과 구현 정확성은 별도다. 기존 infra 승격은 95% 신뢰구간 하한 > 50%와
독립 `seed_offset` 재실행을 따른다. 구조·문서·바인딩·모델 형식 변경 자체에 승률을
요구하지 않는다. 새 AlphaZero 승격 기준은 Phase 10에서 결정하고 전이 실험 수치를
현재 프로젝트의 성능으로 제시하지 않는다.

## 생성물과 자원

Windows의 새로운 프로젝트 생성물 루트는 `%APPDATA%\Accelerate`다. `build`, `cache`,
`datasets`, `models`, `runs`, `reports`, `tmp`로 용도를 구분한다. 빌드·캐시는 OS와
checkout별 고정 슬롯을 사용하고 보존할 실험은 ID·설정·seed·모델/규칙 버전을 남긴다.
캐시 정리와 실험 기록 보존을 구분하며 모델·데이터·보고서를 자동 캐시 정리로 삭제하지 않는다.

WSL2는 일반 개발에 자유롭게 사용한다. 재생성 가능한 Linux 캐시·가상환경·중간 빌드만
`${XDG_CACHE_HOME:-$HOME/.cache}/accelerate`에 둘 수 있다. 보존할 산출물은 호스트의
APPDATA 경로를 확인·변환해 Windows 루트로 내보낸다. CI 루트는 `$RUNNER_TEMP/Accelerate`다.
기존 JS 참고 도구와 CI 생성기는 수정 시 출력 경로를 전환하며 이번 규약 도입으로 출력 계약을 일괄 바꾸지 않는다.

장시간 실행에는 유한한 종료 조건, 자원·worker 설정, 출력, 취소·자식 종료 방법을
기록한다. 기존 process group/Job Object/cgroup/container를 활용할 수 있지만 새 전용
관리자 설치를 일반 작업의 선행 조건으로 만들지 않는다. OOM에서 자원을 조용히 바꾸거나
무한 재시도하지 않는다. 정리는 검증된 소유 경로에 한정한다.

## 구조 검사의 범위

정책 파일은 허용 최상위 경로, 생성물 디렉터리·파일 패턴, 10 MiB 제한을 정의한다.
예외는 정확한 경로, 이유, `generated` 또는 `size` 면제 종류를 명시한다. 최상위 등록,
경로 충돌·비정상 경로·symlink/submodule은 예외로 우회하지 않는다. 소스 영역의 작은
모델 fixture도 생성물 예외를 명시해야 한다. 광범위 wildcard 예외는 허용하지 않는다.

검사기는 Git index에서 stage 0의 경로·mode·object 크기를 얻으며, 내용은 stage된
정책 blob 하나만 읽는다. untracked/ignored 폴더, 파일 내용, symlink 대상, submodule을
순회하지 않는다. stage되지 않은 변경은 검사하지 않으므로 의도한 파일만 stage한 뒤 실행한다.
로컬 작업 중의 모든 쓰기나 코드 규약 전체를 강제 통제하는 도구가 아니다.

```text
node --test .github/scripts/check-repository-policy.test.mjs
node .github/scripts/check-repository-policy.mjs
git diff --cached --check
```

정책 변경도 PR의 검토 대상이다. 검사기를 통과시키려고 생성물을 소스로 등록하거나
필요 없는 면제를 누적하지 않는다. 기존 source·fixture와 정상적인 `build.rs` 이름은
허용하고 실제 생성물만 메타데이터로 거부한다.
