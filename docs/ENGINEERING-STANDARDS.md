# 개발·검증 기준

이 문서는 신규·변경 코드의 품질 기준이다. 에이전트 진입점은 [AGENTS.md](../AGENTS.md),
기여 절차는 [CONTRIBUTING.md](../CONTRIBUTING.md), 구조 검사의 기계 판정 기준은
[repository-policy.json](../.github/repository-policy.json)이다. 같은 규칙의 복제 문서를
영역마다 만들지 말고 해당 기준을 링크한다.

## 근거와 적용 강도

[JPL Power of Ten 원문](https://spinroot.com/gerard/pdf/P10.pdf)은 C 중심의 안전 중요
코딩 원칙이다. [NASA의 NPR 7150.2D 적용 사례](https://gcn.nasa.gov/docs/contributing/npr7150)는
수용 기준, 변경 추적, 검증 근거를 문서와 PR에 연결하는 방식을 보여 준다.
이 프로젝트는 그 신뢰성 원칙을 조정해 사용하며 NASA 분류·인증·전면 준수를 주장하지 않는다.

규칙 엔진·bridge/FFI·데이터 계약·모델 export는 오류가 후속 계산 전체에 전파되는 경계다.
이 영역에서는 입력 검증, 실패의 명시성, 소유권, 버전, 재현 검사를 엄격히 적용한다.
연구 단계에서는 구조와 파라미터의 실험을 허용하되 결과를 채택·승격한 근거와 구분한다.
기존 JS/C++ 전체를 이번 규약에 맞춰 재작성하지 않는다. 기존 경고와 새 경고를 구분한다.

## Power of Ten 조정표

| 원칙 | 처리 | 프로젝트 기준과 검증 |
|---|---|---|
| 단순 제어 흐름·재귀 금지 | 조정 | 명시적 상태 전이. 탐색 재귀는 깊이·노드·시간 한도로 제한하고 한도 도달을 검사한다. |
| 반복 횟수의 고정 상한 | 조정 | 유한한 입력 순회와 작업/step/시간 제한, 취소 경로. 상한 없는 재시도 금지. |
| 초기화 후 동적 할당 금지 | 조정 | 할당을 허용하되 buffer·batch·캐시 한도와 소유권, 자원 부족 오류를 검사한다. |
| 작은 함수 | 적용·조정 | 하나의 변경 이유와 검토 가능한 인터페이스. 60줄 고정 제한 대신 큰 함수의 책임과 분리 가능성을 검토한다. |
| assertion 밀도 | 조정 | 의미 있는 전후 조건·불변식·경계 오류 검사. 함수당 개수 할당이나 항상 참인 assertion 제외. |
| 최소 변수 범위 | 적용 | 전역 가변 상태 최소화. 게임 상태·RNG·모델·캐시의 소유자와 수명을 명시한다. |
| 입력·반환값 검사 | 적용 | 외부 입력 검증과 오류 전파. 기대할 수 있는 입력 실패에 무조건 unwrap/panic하지 않는다. |
| 전처리기 제한 | 조정 | 표준 매크로·PyO3 derive·필요한 feature/cfg 허용. 지원 조합을 명시하고 복잡한 코드 생성은 피한다. |
| 포인터 제한 | 조정 | raw pointer·unsafe를 작은 FFI 경계에 제한. 안전 근거, 수명·동시성·오류 검사를 둔다. |
| 경고·정적 분석 | 적용·조정 | 변경 영역의 compiler/lint/type 검사. 새 경고는 수정하거나 좁은 범위의 이유를 남긴다. |

규약 예외에는 규칙, 이유, 보완 검사, 재검토 조건을 PR에 남긴다. 정당한 예외 때문에
일상적인 구현 선택을 모두 사용자 승인 대상으로 만들지 않는다.

## 에이전트 작업과 검토

1. 변경 상태·기준 커밋·실제 실행 경로를 읽고 관련 계약과 완료 기준을 확인한다.
2. 사용자 요구, 채택된 설계, 제안, 현재 구현, 실행 결과를 구분한다.
3. 담당 영역에서 필요한 변경을 끝까지 수행한다. 미래에 쓸 추상화·복제 구현·빈 디렉터리를
   선제적으로 늘리지 않는다. 기존 영역에 넣을 수 없는 새 책임만 구조 정책에 등록한다.
4. 실패할 수 있는 동작을 중심으로 검사한다. 테스트가 구현의 문장만 재현하지 않게 한다.
5. 별도의 검토 단계에서 실패·취소·자원·동시성·계약·상태 손실을 확인한다.
6. 완료 기준을 실제 결과로 확인하고, 변경 이유·검증 범위·미검증 사항을 보고한다.

불필요한 사용자 확인 없이 승인 범위의 가역적 작업을 진행한다. 중요한 요구의 충돌,
새 비용, 권한을 넘는 외부 변경은 선택과 근거를 구체적으로 설명한다. 다른 작업이나
브랜치의 변경은 보존한다. PR 승인은 기존 팀 리뷰 절차를 따른다.

## 기능 단위 구성과 검사 유지비

SRP는 하나의 기능·변경 이유·소유권에 집중하는 기준이다. 같은 기능의 구현과
관련 보조 코드는 함께 두고, 독립된 책임·재사용·인터페이스 경계가 생기면 분리한다.
작은 함수마다 파일을 만들거나 실험별로 비슷한 구현을 복제하지 않는다. 파일 줄 수나
소스 크기의 합격 기준으로 분할을 강제하지 않는다. 구조 정책의 10 MiB 제한은
무거운 추적 산출물을 막는 기준이며 SRP의 척도가 아니다.

회귀 검사와 fixture는 반복 가능한 중요한 동작을 지킬 때 유지한다. 버그 한 건이나
규약·설계 문구 수정마다 영구 검사를 추가하는 것을 기본 의무로 만들지 않는다.
재발 가능성·영향·기존 검사의 누락과 유지비를 보고 필요한 검사를 선택한다.

- 기존 검사와 fixture를 먼저 활용하고 새 검사는 최소 재현 입력·의미 있는 결과에
  집중한다. 중복 snapshot, 긴 실행 로그, 같은 데이터셋의 버전별 복사본을 쌓지 않는다.
- 신규 fixture는 검증할 계약, 기존 자료로 부족한 이유와 추가 범위를 PR에 설명한다.
  설명을 위해 별도 추적 문서나 전용 관리 도구를 만들지는 않는다.
- 일회성 조사 입력·출력·진단 로그는 `%APPDATA%\Accelerate\reports`에 둔다.
  이후 지속 검증이 필요해진 최소 재현 자료만 소스 fixture로 채택한다.
- 구조 검사·CI와 여러 기물·카드 계약을 검증하는 공통 비교 자료는 실제 사용 가치를
  기준으로 유지한다. 파일 개수·테스트 개수의 고정 할당량을 두거나 기존 유효한
  검사를 일괄 제거하지 않는다. 관련 코드를 바꿀 때 중복·폐기된 검사도 함께 검토한다.

## 경계별 완료 기준

원격 반영이 승인된 작업의 커밋·공유 기본값은 일반 PR 1~3개 논리 커밋, 짧은 작업의
최종 1회 push다. 1시간 초과 작업은 검증된 중간 단계를 공유하고 장기 작업은
60~90분마다 완료 단위가 있는지 확인한다. 시간이나 개수를 맞춘 미완성 커밋은 금지한다.
구체적인 협업 절차는 [CONTRIBUTING](../CONTRIBUTING.md#커밋-크기와-원격-공유-빈도)을 따른다.

| 변경 | 필요한 근거 |
|---|---|
| 저장소 규약·문서 | 문서 간 책임·구현 상태의 일치, 링크, 구조 검사와 그 오류 경로 |
| 규칙 엔진 | 실제 실행 경로의 legal/apply/result, 거절 상태 보존, 턴·종료·RNG, 비교 fixture |
| PyO3 바인딩 | 직접 호출과 JSON의 논리 동등성, 소유권·수명·오류·취소, 필요시 GIL 해제 후 안전성 |
| encoder·데이터 | 충분한 상태/관측 보존, action과 정책 정렬, dtype/shape, 규칙·카탈로그 버전 |
| 모델·ONNX | policy/value 수치 비교, 유한값·mask·batch, FiLM 조건 입력, export 메타데이터 |
| LoRA 병합 | 원본 보존, 호환성·고정 조건 확인, 병합 전후 수치와 성능의 별도 비교 |
| 모델 승격 | 정확성 검사에 더해 독립 seed·색 교환 대전과 정해진 통계 기준 |

일부 signature 일치나 JS 자신과의 회귀를 전체 상태·사이트·Rust 동등성의 증명으로
보고하지 않는다. 실행하지 않은 Rust/Python/ONNX 검사는 미실행으로 기록한다.
학습을 중단한 대국을 실제 무승부·패배 결과처럼 저장하지 않는다. 같은 편 추가 행동이
있으면 MCTS value 부호는 실제 행동자가 바뀔 때 전환한다.

모델 승격과 구현 정확성은 별도다. 기존 infra 승격은 95% 신뢰구간 하한 > 50%와
독립 `seed_offset` 재실행을 따른다. 구조·문서·바인딩·모델 형식 변경 자체에 승률을
요구하지 않는다. 새 AlphaZero 승격 기준은 Phase 10에서 결정하고 전이 실험 수치를
현재 프로젝트의 성능으로 제시하지 않는다.

## 생성물과 자원

Windows의 새로운 프로젝트 생성물 루트는 `%APPDATA%\Accelerate`다. `build`, `cache`,
`datasets`, `models`, `runs`, `reports`, `tmp`로 용도를 구분한다. 빌드·캐시는 OS와
checkout별 고정 슬롯을 사용하고 보존할 실험은 ID·설정·seed·모델/규칙 버전을 남긴다.
캐시 정리와 실험 기록 보존을 구분하며 모델·데이터·보고서를 자동 캐시 정리로 삭제하지 않는다.

WSL2는 일반 개발에 자유롭게 사용한다. 재생성 가능한 Linux 캐시·가상환경·중간 빌드만
`${XDG_CACHE_HOME:-$HOME/.cache}/accelerate`에 둘 수 있다. 보존할 산출물은 호스트의
APPDATA 경로를 확인·변환해 Windows 루트로 내보낸다. CI 루트는 `$RUNNER_TEMP/Accelerate`다.
기존 infra/CI 생성기는 수정 시 경로를 전환하며 이번 규약 도입으로 출력 계약을 일괄 바꾸지 않는다.

장시간 실행에는 유한한 종료 조건, 자원·worker 설정, 출력, 취소·자식 종료 방법을
기록한다. 기존 process group/Job Object/cgroup/container를 활용할 수 있지만 새 전용
관리자 설치를 일반 작업의 선행 조건으로 만들지 않는다. OOM에서 자원을 조용히 바꾸거나
무한 재시도하지 않는다. 정리는 검증된 소유 경로에 한정한다.

## 구조 검사의 범위

정책 파일은 허용 최상위 경로, 생성물 디렉터리·파일 패턴, 10 MiB 제한을 정의한다.
예외는 정확한 경로, 이유, `generated` 또는 `size` 면제 종류를 명시한다. 최상위 등록,
경로 충돌·비정상 경로·symlink/submodule은 예외로 우회하지 않는다. 소스 영역의 작은
모델 fixture도 생성물 예외를 명시해야 한다. 광범위 wildcard 예외는 허용하지 않는다.

검사기는 Git index에서 stage 0의 경로·mode·object 크기를 얻으며, 내용은 stage된
정책 blob 하나만 읽는다. untracked/ignored 폴더, 파일 내용, symlink 대상, submodule을
순회하지 않는다. stage되지 않은 변경은 검사하지 않으므로 의도한 파일만 stage한 뒤 실행한다.
로컬 작업 중의 모든 쓰기나 코드 규약 전체를 강제 통제하는 도구가 아니다.

```text
node --test .github/scripts/check-repository-policy.test.mjs
node .github/scripts/check-repository-policy.mjs
git diff --cached --check
```

정책 변경도 PR의 검토 대상이다. 검사기를 통과시키려고 생성물을 소스로 등록하거나
필요 없는 면제를 누적하지 않는다. 기존 source·fixture와 정상적인 `build.rs` 이름은
허용하고 실제 생성물만 메타데이터로 거부한다.
